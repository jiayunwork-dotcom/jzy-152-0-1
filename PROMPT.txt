我在一家电动工具厂做工业工程。每次新机型导入或者订单量一变，都得重新排总装线的工位：把几十道工序按先后关系分到各工位上，每个工位的作业时间不能超过节拍。现在是我拿 Excel 和便利贴手排，一个机型排一下午，排完也不知道离最优差多远。想做一个后端服务来干这件事，方便我和同事反复试不同节拍。

服务管理「工序图」：一个机型一张图，包含作业编号、作业时间（秒，正数）、紧前关系，还可以有分区约束，即某几道作业必须同工位、某几道作业不能同工位、某道作业只能放在指定工位范围（比如涉及固定设备）。工序图每次修改都生成新版本，旧版本保留，可以按版本号取回。

平衡计算：给定工序图版本和节拍 C，用排序位置权法（位置权 = 自身时间 + 所有直接和间接后继的时间之和）按位置权降序装入工位，同时满足紧前和分区约束；另外实现两种启发式作对照：最大候选规则，以及带随机种子的多次随机装填并取最好结果。每种方法输出各工位的作业集合、工位时间、空闲时间、工位数 K、线效率 Σt/(K·C) 和平滑指数，并附上理论下界：ceil(Σt/C)，以及按作业时间大于 C/2 的个数得到的下界，二者取大。

节拍扫描：给一个节拍区间和步长，对每个节拍跑三种方法，返回每个节拍下的最少工位数和对应方案，并标出效率最高的几个节拍；也可以由日需求量和可用工作时间反推节拍后直接计算。扫描放在后台执行，可查询进度，不同扫描任务可以同时跑。

必须经得起检验的性质：任何输出方案里，每个工位时间都不超过 C；任何作业的紧前作业都在同一工位或更靠前的工位；分区约束全部满足；K 不小于下界；各工位空闲时间之和等于 K·C−Σt；位置权确实包含间接后继（在一条长链上可以手算核对）；同一种子的随机装填结果可以复现；扫描结果中报告的下界随节拍增大单调不增。输入方面，紧前关系成环、引用不存在的作业、作业编号重复、C 小于最长单道作业时间、分区约束彼此矛盾（例如必须同工位的两道作业又被要求不能同工位），都要在计算前拒绝，并指出具体涉及哪几道作业。某些节拍下约束无法满足时，该节拍标为不可行并说明原因，不影响扫描的其余部分。仓库里放一个十几道作业的水泵装配示例，前几步装填可以手算。

技术上定为 Spring Boot 3 on Java 17，依赖和打包交给 Maven。工序图模型与校验、后继闭包计算、三种装填算法、下界计算、节拍扫描、任务调度、版本存储、接口层分包，每种算法单独成类。工序图版本和计算结果存 PostgreSQL 16。JUnit 5 覆盖上面的性质，随机装填部分用多个种子做性质测试。应用容器沿用 maven 仓库里 3.9 + JDK17（eclipse temurin 发行版）那个标签，数据库用 postgres:16-alpine，两者写进同一份 compose 文件，服务只提供 HTTP 接口，不做页面。
